# 状态与故障恢复

## 网页正常但 RSS 搜索失败

先区分 `/rss.xml` 最新流与 `/rss.xml?keyword=…` 搜索。2026-10-30 旧路径 `/topics/rss/rss.xml?keyword=…` 返回 404，已改为新路径并保留旧路径备用。页面可访问或工作流整体成功，不代表每条搜索都成功，应查看日志中的失败 URL 和状态码。

适配器在请求失败、返回 HTML 或无效 XML 时尝试镜像与旧入口，不绕过浏览器验证；有效空 RSS 不当成故障。所有入口均失败时保留异常状态并说明功能受限，不能通过删除 state 或重新订阅解决。

## 文件职责

`config.json` 保存规则，`state.json` 保存版本化基线、待发送消息、检查状态与最近送达信息。
`state.backup.json` 保存上一次有效主状态。云端工作流会一并提交主状态和备份。

`fallback_waiting` 保存按规则和集号区分的首次观察时间与最优候选，正式检查和加番共用 7 天等待期。不要删除这些记录来刷新倒计时；暂停、删除或修改匹配条件会取消相应旧等待。指定组出现时取消等待及尚未送达的该集兜底消息。已满等待期的候选仍保留首次观察时间，避免下一次检查重新等待。

旧状态首次读入会在内存迁移到 `state_version=1`，保留已有规则 ID 和两段/三段去重键；只有正式保存时才落盘。组名等价时复用旧键，不删除旧历史。

## 损坏与缺失

1. 主状态损坏/缺失、备份有效：读取备份并记录恢复警告；只查看时不覆盖文件，正式运行后保存恢复状态。
2. 主状态和备份均损坏：程序停止，不静默建立空基线。请从 Git 历史恢复最近一次成功运行的状态。
3. 两个文件都不存在：按新部署处理。已有项目不要同时删除这两个文件，否则可能重新推送历史。

手动恢复前先保存现有文件，暂停外部定时器，确认要恢复的提交日期与规则版本一致。PowerShell 示例：

```powershell
Copy-Item -LiteralPath .\state.json -Destination .\state-before-recovery.json
Copy-Item -LiteralPath .\state.backup.json -Destination .\state.json
python add_rule.py --validate
python acgnx_watch.py --once --dry-run
```

若主状态不存在，跳过第一条复制。检查输出后再恢复定时器。备份可能比主状态少一轮数据，恢复后仍有少量重复窗口。

## 抓取失败

有效空 RSS 与网络/解析失败分开记录。部分源成功显示 partial；全部源失败不推进初始化或集数基线，单轮命令返回非零退出码，状态保存步骤仍会执行。

默认连续失败 3 次发送一次告警；持续失败不每轮刷屏，恢复后发送一次恢复提示。网站整体不可用时，总告警会列出受影响番剧，不再逐部重复发送；恢复时合并成一条，仍有番剧搜索失败会明确列出。独立的单部番故障仍保留监测，同轮多部番的告警或恢复合并通知。可在 settings 设置 `failure_alert_after`。推送服务本身不可用时，告警也进入待发送队列。

## 消息发送与 Git 保存

回溯通知和正常单集均按任务内容生成稳定队列键。基线与待发送任务一并保存后才发送，逐条确认成功并立即保存收据；失败保留原消息重试，即使资源已经退出 RSS 也不依赖重新抓到它。基线表示已纳入处理，并不等于已送达，待重试数量及最近送达信息才反映发送结果。Git 提交失败会使 Actions 失败并保留可查日志。

**外部推送与远端 Git 提交不是原子事务。** 逐条保存缩小了进程中断的重复窗口，但服务收到消息到本地收据保存之间，以及本地状态到远端 Git 提交之间，仍有重复窗口。本项目不承诺 exactly-once。遇到这种情况先恢复状态提交，不要反复重跑旧任务。

`--reset-state` 是明确重建基线的操作，会同时重置主状态与备份。仅在理解后果时使用，不用它来处理普通重复推送问题。

## 云端远端检查点与运行预算

三个云端写入工作流的发送步骤启用 `ACGNX_REMOTE_CHECKPOINT=1`：保存状态时先将 config/state/backup 提交到远端 main；待发送队列在第一次外部发送前已经进入 Git，成功收据逐条提交。任何检查点失败都会中止后续发送，最后的工作流保存步骤仍会尽力保存本地结果。

远端检查点只允许在 Actions 的 main 检出中启用。本地默认关闭，不会自动推送；离线测试与 PR CI 也关闭。单次检查点总预算 45 秒、单条 Git 命令最多 25 秒，错误不打印带凭据的远端地址。

正式云端抓取共享 120 秒网络预算；发送共享默认 240 秒预算和最多 12 次尝试（包含旧重试与新通知）。预算耗尽时保留队列，下轮继续，给状态保存留出时间。settings 可设置 `max_pushes_per_cycle`（1..12）和 `send_budget_seconds`（120..240）。发送服务接收与收据提交仍不是原子事务，中断在该窄窗口内可能重发；不要把预算和检查点当成 exactly-once 保证。

## 集号迁移

`episode_maps` 保存明确的累计号与季内号对应关系。迁移添加规范键、保留旧键及最优档位／最大修订号；可能看到去重键数量增加，不能把键数量当成实际集数。等待缓存合并等价集号时保留最早观察时间。升级会清理明确非动画的等待候选，保留其他等待的原始起点。

## Issue 永久清理失败

先确认规则已从 config.json 和《我的番剧》中移除，再查看 issue-rule.yml 的“回复 Issue”日志。永久清理失败不回滚已保存的规则删除，也不会重发删除通知；失败时仅静默关闭操作 Issue。

检查 `ACGNX_ISSUE_DELETE_TOKEN` 名称、令牌是否到期或撤销、是否属于个人仓库所有者及是否具备所需权限。公开仓库的 classic 令牌使用 `public_repo`；不要为了清理 Issue 授予 `delete_repo`。更换令牌后更新同名 Secret，无需重启。

永久删除的 Issue 无法通过普通关闭/重新打开流程恢复；恢复 Git 提交也不会恢复已删除的 Issue。2026-10-19 的固定历史清理任务只处理当时保存的 61 条目标，不扫描或删除之后新建的 Issue，不要把它当作常规自动整理任务。

飞书历史消息与 GitHub 状态分别保存。恢复配置或删除 Issue 不会撤回飞书消息；当前 Webhook 渠道没有自动撤回，客户端操作仍受身份和时限限制。
